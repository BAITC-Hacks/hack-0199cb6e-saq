# ЕКТ — Автозаказ поставщикам

**Рекомендации по закупкам для ТОО «Электрокомплект»: сколько заказать у Systeme Electric и ИЭК и почему.**

Проект помогает менеджеру по закупкам подготовить заказ на основе Excel-выгрузок из 1С. Формат решения — локальный Python-движок; результат — таблица рекомендаций с обоснованиями и экспортом в CSV. Окончательное решение о заказе принимает сотрудник.

Проект разработан для кейса ТОО «Электрокомплект» на HACKALEM AI.

## Для кого и какую проблему решаем

Основной пользователь — менеджер по закупкам, который отвечает за наличие электротехнической продукции и пополнение склада.

Для подготовки заказа ему нужно совместить продажи, остатки, ожидаемые поставки, сезонность и условия закупки. Простое среднее продаж может дать неверную потребность: отсутствие товара скрывает часть спроса, а разовый крупный заказ завышает обычный уровень. Если не учесть товар в пути, можно заказать лишнее; если не учесть срок поставки — получить дефицит до прихода следующей партии.

Цель решения — сократить ручную сверку таблиц и дать проверяемое обоснование количества по каждой позиции. Закупщик должен видеть, какие факторы увеличили или уменьшили рекомендацию, прежде чем принять решение.

## Состав текущего решения

Команда сократила объём до Python-движка и табличного результата / CSV-экспорта. Основные критерии приёмки:

| Критерий | Что должно быть в результате |
|---|---|
| MH1 — учёт источников | Потребность учитывает историю, остатки, товар в пути, категории и прогноз прироста |
| MH2 — сезонность и рост | Прогноз учитывает сезонные изменения и устойчивый тренд |
| MH3 — упущенный спрос | Периоды отсутствия товара учитываются при восстановлении спроса |
| MH4 — разовые заказы | Аномальные разовые покупки отделяются от регулярных крупных закупок |
| MH5 — объяснения | Рекомендации сгруппированы по поставщикам; количество каждой строки имеет обоснование |

**Статус интеграции:** движок и исправление адаптера готовятся в отдельной ветке команды. Эта ветка обновляет документацию; успешная приёмка MH1–MH5 здесь не заявляется. Ниже описана методология из спецификации, с которой сверяется итоговая реализация.

## Как работает решение

Целевой сквозной сценарий для интегрированной версии:

1. Подготовить Excel-выгрузки из 1С: продажи, остатки, условия закупки, сезонность и ожидаемые поставки.
2. Загрузить их через адаптер и проверить сообщения о качестве: пустые количества, дубликаты, неизвестные товары и расхождения между отчётами.
3. Выполнить расчёт потребности с выбранными параметрами поставок и пополнения.
4. Получить таблицу / CSV с рекомендациями по поставщикам, проверить количества, единицы закупки и объяснения.
5. При необходимости скорректировать параметры и повторить расчёт. Подготовку окончательного заказа выполняет ответственный сотрудник.

Автоматическая отправка заказа поставщику не предусмотрена.

## Данные

Источники кейса — **12 Excel-выгрузок из 1С**, по шесть для Systeme Electric и ИЭК.

| Данные | Назначение |
|---|---|
| Месячные продажи | Базовая история спроса в количестве |
| Строки расходных накладных | Поиск разовых крупных покупок, анализ повторяемости и возвратов |
| Остатки на начало месяца | Выявление периодов возможного отсутствия товара |
| MOQ и кратности | Минимальная партия и допустимый шаг заказа |
| Коэффициенты сезонности | Дополнительная информация о сезонном профиле поставщика |
| Рабочая таблица SE / «Путь» ИЭК | Атрибуты товаров, доступные остатки, поставки и ожидаемые даты поступления |

По описанию набора дата среза — 22.09.2026. Полная месячная история охватывает январь 2024 — август 2026; неполный сентябрь не используется как полный месяц для прогноза. Транзакции с января 2025 позволяют исследовать отдельные накладные.

Текущий остаток SE берётся из рабочей таблицы. У ИЭК нет отдельного снимка на дату: предусмотрена оценка по начальному остатку и последующим продажам, которую необходимо явно помечать как оценочную.

Коды 1С сохраняются строками, включая ведущие нули, регистр и завершающий `_`. Единицы продажи и закупки могут различаться: метры и бухты, штуки и упаковки.

Реальные выгрузки хранятся вне репозитория. Для воспроизводимой проверки предусмотрены синтетические сценарии. Сырые идентификаторы клиентов не допускаются; при необходимости клиентского признака используется обезличенный `client_hash`.

## Методология расчёта потребности

Методология задана в [SPEC_ENGINE.md](docs/SPEC_ENGINE.md). Количества рассчитываются детерминированными правилами и статистическими методами; генеративный ИИ для расчёта не требуется.

1. **Подготовка истории.** Используются полные месяцы; возвраты и отрицательные значения обрабатываются отдельно, чтобы не искажать обычный спрос.
2. **Очистка разовых всплесков.** Из месячной истории исключается только подтверждённый избыточный объём разовых покупок. Регулярные крупные покупки сохраняются.
3. **Восстановление спроса.** По остаткам и датам продаж оценивается доступность товара. Продажи в период дефицита корректируются с ограничением сверху, чтобы восстановление не давало необоснованного роста.
4. **Прогноз.** Оцениваются уровень спроса, сезонность и устойчивый тренд. Для редкого и нерегулярного спроса предусмотрен отдельный подход; ручной прогноз прироста применяется явно.
5. **Пополнение.** Горизонт покрытия включает срок поставки и период пересмотра заказа. К спросу на этот горизонт добавляется страховой запас, затем вычитаются доступный остаток и поставки, ожидаемые в пределах горизонта.
6. **Условия закупки.** Применяются ограничения покрытия, перевод в единицы закупки, MOQ и кратность. Поздние поставки не считаются доступными раньше своей даты поступления.

Базовая формула до ограничений и округления:

```text
Потребность = max(0,
    прогноз спроса на срок поставки и период пересмотра
    + страховой запас
    − доступный остаток
    − поставки, ожидаемые в этом горизонте)
```

Объяснение количества строится как последовательность вкладов: базовый спрос, сезонность, тренд, прирост, страховой запас, остатки, поставки и округление. Сумма вкладов должна совпадать с итоговым количеством в соответствующих единицах; это отдельная проверка приёмки.

## Как исключаются разовые крупные заказы

Большая накладная сама по себе не означает разовый спрос. В спецификации предусмотрены следующие шаги:

1. Для каждого товара положительные строки расходных накладных сравниваются с типичными объёмами через медиану, устойчивую оценку разброса и верхний процентиль. Учитывается доля строки в месячных продажах.
2. Проверяется повторяемость: сопоставимые крупные строки минимум в четырёх из последних 12 месяцев считаются регулярным паттерном. При наличии обезличенного клиентского признака учитывается и повторяемость покупок клиента.
3. У разовой строки определяется избыточная часть сверх обычного объёма. Из месячных продаж вычитается только та её часть, которая действительно отражена в месячном отчёте:

   ```text
   Вычитание = min(разовый избыток,
                  max(0, месячные продажи − регулярные транзакции))
   ```

4. Для месяцев без детализации по накладным предусмотрена дополнительная проверка резких месячных всплесков с учётом сезонности.

Такая проверка важна для IMT35100: по ручной сверке команды крупные строки повторяются во всех последних 12 месяцах, поэтому паттерн признан регулярным. Отдельно обрабатываются неизвестные товары: например, чужой SKU LOOP должен попадать в карантин при загрузке. Карантин и исключение разового объёма — разные операции.

## Технологии и архитектура

| Технология / формат | Роль |
|---|---|
| Python | Расчётный движок и обработка данных |
| pandas | Преобразование и сопоставление таблиц |
| openpyxl | Чтение Excel-выгрузок |
| CSV | Экспорт итоговой таблицы рекомендаций |

```text
Excel-выгрузки из 1С
        ↓
Адаптеры: чтение, нормализация и проверка качества
        ↓
Канонические таблицы
        ↓
Python-движок: очистка → восстановление спроса → прогноз → пополнение
        ↓
Рекомендации с объяснениями → таблица / CSV → проверка закупщиком
```

Веб-интерфейс, Next.js, API/FastAPI, Ollama, голос, казахский ИИ-чат, RBAC и аудит исключены из текущего объёма. Полный стек в первоначальном PLAN.md не описывает состав сдаваемой версии.

## Как проверить решение

После интеграции запуск должен воспроизводиться на синтетических данных. Сценарии приёмки заданы в [SPEC_ENGINE.md §5](docs/SPEC_ENGINE.md):

| Сценарий | Ожидаемая проверка |
|---|---|
| Увеличить остаток или ближайшую поставку | Потребность уменьшается при прочих равных |
| Добавить устойчивый рост и сезонный профиль | Прогноз отражает оба фактора |
| Добавить период отсутствия товара | Восстановленный спрос учитывается в потребности и объяснении |
| Добавить одиночную аномальную покупку и регулярные крупные покупки | Разовый избыток исключается, регулярный паттерн сохраняется |
| Проверить итоговую таблицу | Есть группировка по поставщикам, объяснения и согласованность суммы вкладов с количеством |
| Проверить единицы и повторный запуск | Заказ соответствует единицам закупки и кратности; одинаковые входы дают одинаковый результат |

Результаты ручной сверки исходных данных и открытые вопросы собраны в [DATA_CHECK.md](docs/DATA_CHECK.md). Они не заменяют тестирование адаптера и движка. Метрики точности, экономии и производительности до измерений не заявляются.

## Ограничения

- Исправление адаптера и интеграционная проверка ещё выполняются командой; воспроизводимый запуск должен быть добавлен перед окончательной сдачей.
- Оценка остатка ИЭК и восстановление спроса при дефиците зависят от полноты исходных данных.
- Между транзакциями и месячными отчётами есть расхождения; численные вопросы зафиксированы в DATA_CHECK.md и требуют сверки.
- CSV служит результатом для проверки человеком. Прямая загрузка этого CSV в 1С не подтверждена.
- Подтверждение и отправка заказа остаются действиями сотрудника. Публичная веб-версия в текущем объёме не предусмотрена.
